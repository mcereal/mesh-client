# Text and translation

Every word the user reads comes from one file. A screen names a *string id* and
[`src/i18n/strings.c`](../src/i18n/strings.c) answers with the text for the language in force,
exactly the way [`src/ui/theme.c`](../src/ui/theme.c) answers a colour role. That is what makes
a language switch total instead of a hunt: no renderer holds an opinion about English, so there
is nowhere for an untranslated sentence to hide.

The client ships English and Spanish (Español). Select **Settings → About MeshClient →
Language** and press A to cycle languages. The choice applies immediately and survives a
relaunch. In Spanish, the same row is **Ajustes → Sobre MeshClient → Idioma**.

```
include/mesh/i18n/catalog.def   the catalog: one line per string, English text and a comment
include/mesh/i18n/strings.h     enum mesh_str_id, mesh_str(), the locale API
src/i18n/strings.c              the English table, the locale registry, lookup and validation
src/i18n/locale_es.c            the complete Spanish table
scripts/gen-locale.py           catalog -> a .pot for a translator, or a locale .c skeleton
scripts/check-strings.py        fails the build when a renderer spells a sentence out
tests/suites/i18n.c             the catalog is complete; a translation keeps its arguments
```

## Adding a string

One line in `catalog.def`, and use it:

```c
MESH_STR_ENTRY(TOAST_SENT_TO, "Sent to %s")
```

```c
mesh_str_format(toast, sizeof toast, MESH_STR_TOAST_SENT_TO, name);
```

The enum, the English table, the id names and both generator outputs are all expansions of that
one list, so there is no second place to update and nothing to keep in step.

Three primitives cover every use:

| | |
|---|---|
| `mesh_str(id)` | the text, never NULL; use it where a `const char *` is wanted |
| `mesh_str_format(out, len, id, ...)` | `snprintf()` with a catalog entry as the format |
| `mesh_str_plural(one_form, n)` | picks the form `n` takes by the locale's own rule |

There are two convenience wrappers over the same idea, both for places that were already
formatting: `mesh_ui_line_str()` appends a formatted entry to a `struct mesh_ui_line`, and
`fb_draw_status_row()` takes the label and the value as ids. `fb_draw_status_text()` is its
sibling for a value that is already text.

### Rules for an entry

- **One whole sentence or label per id, %-specifiers included.** Never build a sentence by
  concatenating two catalog entries. Word order is the translator's to change, and a caller that
  glues two halves together has taken that away.
- **The id says where it is read, not what it says.** `TOAST_SEND_FAILED`, not
  `SEND_FAILED_TEXT`. An id is forever; the English behind it is not.
- **A word doing two jobs gets two ids.** "off" under Bluetooth and "off" as a duration are one
  word in English and two in most other languages. `COMMON_OFF` and `ZERO_OFF` are separate for
  exactly that reason.
- **Write the comment for a translator.** A string with no context is a string that gets
  translated wrong, and `gen-locale.py` carries the comment into what they see.
- **Mind the width.** The Brick's panel is about 40 cells at the body scale, and the action bar
  along the bottom is one line of keycap-and-verb pairs. A translation that runs longer than the
  English is the one that gets clipped; the entries that are tightest say so in their comments.
  The `ACTION_*` verbs are the tightest of all, and they fail differently from everything else:
  the bar drops actions from the *end* rather than wrapping, so a long verb does not overrun -
  it costs whichever action was written last its place on screen.

## What is deliberately not in the catalog

Not everything that is a string is text.

- **Log lines.** `mesh_log()` output is for whoever is reading `make deploy-logs`, and a bug
  report in a language the maintainer cannot read is worse than no bug report. Where a log and
  a screen want the same sentence, keep one mapping and let each caller pick its language:
  `mesh_str(id)` for the screen, `mesh_str_in(mesh_i18n_locale_english(), id)` for the log.
  `mesh_message_ack_error_id()` in [`src/core/message.c`](../src/core/message.c) is the worked
  example - a bubble reads it in the user's language and the log in English, off one table.
- **Names shared with the rest of Meshtastic**: region codes (`EU 868`), hardware models
  (`Heltec V3`), modem presets (`Long Range - Fast`), device roles (`Router`). A setting read
  off the Brick has to be recognisable in the phone app and back, which is the same reason a
  channel key is shown as base64. They stay in
  [`src/core/radio_settings.c`](../src/core/radio_settings.c).
- **Protocol, path, environment and config text.** Nobody reads it as prose.
- **`src/main.c`'s `--help` and the `cli`/`stub` backends.** Those are the headless developer
  surfaces; they never reach the device screen. `mesh_message_ack_to_string()` is only read by
  those two, which is why it is untranslated while `mesh_message_ack_error_to_string()` beside
  it - the one a toast shows - is not.
- **A transport's waiting reason** (`"BlueZ service not present; waiting for bluetoothd"`) is
  logged, not shown. What a transport *does* show goes through `mesh_ble_set_error()` and
  `mesh_serial_set_error()`, whose first parameter is an `enum mesh_str_id` - a literal there
  does not compile.

## Adding a language

1. `./scripts/gen-locale.py stub de -o src/i18n/locale_de.c` writes a skeleton: every id, its
   English text as a comment, and `NULL` for the translation. (`gen-locale.py template` writes a
   gettext-like `.pot` instead, if the translator would rather work in that.)
2. Fill in the entries. **A `NULL` is not an error** - it reads as English - so a partial
   translation ships and reads as a mixture rather than as blank rows, which is the state every
   translation is in for a while.
3. Add the file to `MESHCLIENT_CORE_SOURCES` in `CMakeLists.txt`.
4. Add a row to `k_locales` in `src/i18n/strings.c`:

```c
extern const char *const mesh_i18n_table_de[MESH_STR_COUNT];

static const struct mesh_i18n_locale k_locales[] = {
    {.id = "en", .name = "English", .table = NULL, .plural_form = plural_english},
    {.id = "de", .name = "Deutsch", .table = mesh_i18n_table_de, .plural_form = NULL},
};
```

`name` is the language's own name for itself - "Deutsch", not "German". It is what a picker
shows, and a picker is only usable if its entries are in the languages they name. It is a
required field rather than a catalog entry on purpose: a catalog entry may be left
untranslated, and a locale whose name fell back to English would have Settings → About
reporting the wrong language while that language was on screen.

5. `make test`. `mesh_i18n_validate()` runs over every locale in the build and rejects a
   translation whose %-specifiers no longer match the English.

### Choosing one at runtime

`mesh_i18n_init()` runs before anything can draw, and reads, in order: `MESHCLIENT_LANG`,
`LC_ALL`, `LC_MESSAGES`, `LANG`. Each is matched on the language part alone, so `fr_CA.UTF-8`
finds `fr`; `C` and `POSIX` mean "no language", not a request for one; anything unknown leaves
English in force. `MESHCLIENT_LANG` comes first so `launch.sh` can pin a language without
touching a system locale, which on a handheld running MinUI is not something a user can set.

The saved `language` id in `ui_prefs` takes precedence over the system locale variables.
An explicit, nonempty `MESHCLIENT_LANG` (other than `C` or `POSIX`) takes precedence over the
saved choice and makes the Language row read-only, labelled “Language (env)”. For example,
`MESHCLIENT_LANG=es` or `MESHCLIENT_LANG=es_PR.UTF-8` selects Spanish. An unknown explicit
override falls back to English; an unknown saved id follows the system locale instead.

The picker cycles the locale registry, so registering another language automatically makes it
selectable. It saves the id immediately and republishes the snapshot before the redraw, because
snapshots contain formatted text. Built-in quick replies and date separators follow the selected
language; custom `canned.txt` replies are preserved verbatim.

## Why the formats are checked at runtime

A catalog entry carries its own `%`-specifiers, because `"Sent to %s"` has to be one string: a
language that puts the verb last cannot translate the halves. That makes the format
non-literal, which `-Wformat=2` rightly objects to, so the objection is answered in exactly one
place - `mesh_str_vformat()` in `src/i18n/strings.c`, the only function in the client that
formats a string it did not write.

What the compiler stops checking, `mesh_i18n_validate()` checks instead: for every entry a
locale translates, the sequence of specifiers - their order, their length modifiers, the `*`
that eats an argument of its own - has to match the English exactly. Reordering the *words* is
the whole point of a translation and is fine; turning `"%u of %u"` into `"%s of %u"` is a crash,
not a typo, and the tests reject it before it can reach a `vsnprintf`.

## Plurals

`MESH_STR_PLURAL_ENTRY(id, "one", "other")` declares two consecutive ids, and
`mesh_str_plural(MESH_STR_id_ONE, n)` picks between them by the *locale's* rule rather than by
`n == 1` at the call site - which is an English rule, and not even that in every sentence.

Two forms is what `MESH_STR_PLURAL_FORMS` allows, which covers English, Spanish, German, Dutch and the
Scandinavian languages. Polish and Russian need three, Arabic six. Widening it is that constant,
the `MESH_STR_PLURAL_ENTRY` macro in `strings.h`, and the tables - nothing at any call site,
because a call site already asks the locale rather than counting for itself.

## Known gaps

- **The font.** [`src/ui/font5x7.c`](../src/ui/font5x7.c) covers ASCII plus composed accented
  Latin, so Western European languages draw today. Greek, Cyrillic and anything CJK need glyphs
  the font does not have and would render as the replacement box. Adding accented Latin is a
  line in that file's table; a script is not.
- **The on-screen keyboard is QWERTY only.** `k_kb_layers` in
  [`src/ui/nav_keyboard.c`](../src/ui/nav_keyboard.c) is the keys themselves rather than words
  about them, so it is not a catalog entry. A locale that wants AZERTY needs a second layout
  table and a way to choose it - a small change, but a different one from translating text.
- **Numbers use `printf`.** The decimal separator is a point everywhere. Date separator
  weekday and month names come from the catalog; clock times retain the 24-hour format.
- **No right-to-left support.** The framebuffer draws left to right and measures in cells.

## Keeping it honest

`scripts/check-strings.py` reads the files that draw or announce something and fails on any
string literal that looks like prose - three letters in a row, outside a comment, outside a log
call. It runs as part of `make test`. Everything a renderer legitimately spells out (printf
glue, a path, the keyboard's own keys) is listed in `ALLOWED` in that script, each with the
reason it stays; add to that list only when the string genuinely is not something a person
reads.

`tests/suites/i18n.c` covers the rest: the catalog is complete and its ids and text line up, a
partial translation falls back entry by entry, a translation that drops or retypes an argument
is rejected, plurals pick the locale's form, and the environment resolves the way the section
above says it does.
