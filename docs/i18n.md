# Text and translation

A screen names a *string id* and [`src/i18n/strings.c`](../src/i18n/strings.c) answers with the
text for the language in force, the way [`src/ui/theme.c`](../src/ui/theme.c) answers a colour
role. No renderer holds an opinion about English, so there is nowhere for an untranslated
sentence to hide.

English and Spanish ship. **Settings → About MeshClient → Language**, A to cycle; the choice
applies immediately and survives a relaunch.

```
include/mesh/i18n/catalog.def   the catalog: one line per string, English text and a comment
include/mesh/i18n/strings.h     enum mesh_str_id, mesh_str(), the locale API
src/i18n/strings.c              the English table, the locale registry, lookup and validation
src/i18n/locale_es.c            the complete Spanish table
scripts/gen-locale.py           catalog -> a .pot for a translator, or a locale .c skeleton
scripts/check-strings.py        fails the build when a renderer spells a sentence out
tests/suites/i18n.c             the catalog is complete; a translation keeps its arguments
```

## Adding a string

One line in `catalog.def`, and use it. The enum, the English table and both generator outputs
are all expansions of that one list.

```c
MESH_STR_ENTRY(TOAST_SENT_TO, "Sent to %s")
mesh_str_format(toast, sizeof toast, MESH_STR_TOAST_SENT_TO, name);
```

| | |
|---|---|
| `mesh_str(id)` | the text, never NULL |
| `mesh_str_format(out, len, id, ...)` | `snprintf()` with a catalog entry as the format |
| `mesh_str_plural(one_form, n)` | picks the form `n` takes by the locale's own rule |

`mesh_ui_line_str()` and `fb_draw_status_row()` are wrappers over the same idea for callers that
were already formatting.

### Rules for an entry

- **One whole sentence or label per id, %-specifiers included.** Never concatenate two entries
  into a sentence — word order is the translator's to change.
- **The id says where it is read, not what it says.** `TOAST_SEND_FAILED`, not `SEND_FAILED_TEXT`.
- **A word doing two jobs gets two ids.** "off" under Bluetooth and "off" as a duration are one
  word in English and two elsewhere: `COMMON_OFF` and `ZERO_OFF`.
- **Write the comment for a translator.** `gen-locale.py` carries it into what they see.
- **Mind the width.** The panel is about 40 cells at body scale. The `ACTION_*` verbs are
  tightest and fail differently: the bar drops actions from the *end* rather than wrapping, so a
  long verb costs whichever action was written last its place on screen.

`MESH_STR_PLURAL_ENTRY(id, "one", "other")` declares two consecutive ids. Two forms covers
English, Spanish, German, Dutch and the Scandinavian languages; Polish and Russian need three,
Arabic six. Widening it is `MESH_STR_PLURAL_FORMS`, the macro and the tables — no call site,
because a call site already asks the locale rather than counting for itself.

## What is deliberately not in the catalog

- **Log lines.** A bug report in a language the maintainer cannot read is worse than none. Where
  a log and a screen want the same sentence, keep one mapping: `mesh_str(id)` for the screen,
  `mesh_str_in(mesh_i18n_locale_english(), id)` for the log. `mesh_message_ack_error_id()` is the
  worked example.
- **Names shared with the rest of Meshtastic**: region codes, hardware models, modem presets,
  device roles. A setting read off the Brick has to be recognisable in the phone app and back.
  They stay in [`src/core/radio_settings.c`](../src/core/radio_settings.c).
- **Protocol, path, environment and config text**, and `src/main.c`'s `--help` and the
  `cli`/`stub` backends — headless developer surfaces that never reach the device screen.
- **A transport's waiting reason** is logged, not shown. What a transport *does* show goes
  through `mesh_ble_set_error()`, whose first parameter is an `enum mesh_str_id` — a literal
  there does not compile.

## Help notes: the one class a locale may omit

Every id must be translated before a language ships. The one exemption is keyed on the id's own
name: `SETTINGS_NOTE_*`, the help screen's paragraphs (see [`help.md`](help.md)). They are
paragraphs rather than labels, they are technical prose about a regulated transmitter where a
mistranslation is wrong advice, and they already degrade per id through `mesh_str_in()`. A note
may be left `NULL` indefinitely. Everything else is held to the full bar.

## Adding a language

1. `./scripts/gen-locale.py stub de -o src/i18n/locale_de.c` writes a skeleton. (`template`
   writes a gettext-like `.pot` instead.)
2. Fill entries in. **A `NULL` is not an error** — it reads as English, so a partial translation
   ships as a mixture rather than as blank rows.
3. Add the file to `MESHCLIENT_CORE_SOURCES` in `CMakeLists.txt`.
4. Add a row to `k_locales` in `src/i18n/strings.c`. `name` is the language's own name for
   itself — "Deutsch", not "German" — and is a required field rather than a catalog entry,
   because a name that fell back to English would report the wrong language while that language
   was on screen.
5. `make test`. `mesh_i18n_validate()` rejects a translation whose %-specifiers no longer match
   the English: reordering words is the point of a translation, but turning `"%u of %u"` into
   `"%s of %u"` is a crash. This is also why `mesh_str_vformat()` is the one function in the
   client that formats a string it did not write — the catalog's formats are non-literal by
   design, so `-Wformat=2` is answered in exactly one place.

`mesh_i18n_init()` reads `MESHCLIENT_LANG`, `LC_ALL`, `LC_MESSAGES`, `LANG`, matching on the
language part alone. The saved `language` in `ui_prefs` takes precedence over those; an explicit
`MESHCLIENT_LANG` takes precedence over the saved choice and makes the row read-only, labelled
"Language (env)". `MESHCLIENT_LANG` comes first so `launch.sh` can pin a language without a
system locale, which on a handheld running MinUI a user cannot set.

## Known gaps

- **The font.** [`src/ui/font5x7.c`](../src/ui/font5x7.c) covers ASCII plus composed accented
  Latin. Greek, Cyrillic and CJK render as the replacement box. Adding accented Latin is a line
  in that table; a script is not.
- **The on-screen keyboard is QWERTY only** (`k_kb_layers` in `src/ui/nav_keyboard.c`). Its
  layers are the layout rather than text, so they are not in the catalog: a locale wanting AZERTY
  needs a second table here, not a translation of this one. The emoji layer beside them
  (`k_kb_emoji`) is not translated either, for the stronger reason that it is glyphs.
- **Numbers use `printf`** — the decimal separator is a point everywhere, and clock times are
  24-hour. Weekday and month names do come from the catalog.
- **No right-to-left support.**

`scripts/check-strings.py` runs as part of `make test` and fails on any literal in a rendering
file that looks like prose. Legitimate exceptions are listed in `ALLOWED` in that script, each
with its reason.
